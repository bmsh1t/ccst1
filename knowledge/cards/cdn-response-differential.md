# CDN/DNS 差分与响应语义判别

## Quick Recall

- 触发：目标在 CDN/反向代理之后（响应头、CNAME、多解析结果或测绘指纹提示），或路径探测
  得到大量同形响应，无法区分真实存在与统一兜底。
- 最小验证：多 resolver 解析对比、同方法随机 miss 对照、固定大小差分、扩展名直通路径探测，
  每次只改变一个变量。
- 证据门：状态码差异只证明处理分支不同；证明入口存在需要可复现的响应结构差、错误族差或
  协议级行为差，并绑定具体请求与响应证据。
- 停止：需要真实源站访问、凭据、云资源枚举或对后端的盲写利用时按红线收敛，差分证据只作为
  Signal/Lead 记录。

## 触发信号

- 目标位于 CDN/反向代理之后：响应头、CNAME 指向、多 resolver 解析结果或测绘指纹提示。
- 路径探测得到大量同形响应，无法区分真实存在与统一兜底。
- 管理路径或敏感路径在不同状态码（502/403/404）间表现不一致。
- 子域解析结果高度同质，怀疑通配符 DNS。

## 能力定位

本卡用于 recon 与路径发现阶段，补充 CDN/代理环境下的判别语义：DNS 解析差分、状态码过滤语义、
catch-all 识别和源站定位线索。输出候选假设、发散问题和最小验证提示，不替代工具执行。

## 核心判别模式

### 1. 多 resolver DNS 差分

- 地域策略 CDN 可能对部分公共 resolver 返回 `0.0.0.0` 或占位地址，对另一些返回真实节点；
  用至少两个不同网络的 resolver 对比同一主机名的解析结果，差异本身即 CDN 地域策略证据。
- 通配符 DNS 识别：随机长前缀子域（如 `random123456.target.com`）也解析到已知 CDN 节点
  说明是通配符记录；此时子域枚举无意义，所有 IP 都是 CDN 节点，源站需从历史 DNS、证书透明、
  同服务器其他域名、邮件头或 SSRF 类渠道获取。
- 多 resolver 一致返回同一非 CDN IP 是源站候选的直接证据；单点差异先怀疑解析缓存或地域
  调度，复测后再记录。

### 2. CDN 状态码过滤语义

- 同一路径下 CDN/反代可能改写后端语义：`502` 可能表示后端响应被过滤（路径在源站存在），
  `404` 通常是源站真不存在，`403` 是代理层路由拒绝。三者构成差分枚举的基线，不能按字面
  语义直接解释。
- 差分用法：用同方法对照一个确定存在的路径与一个确定不存在的路径，观察中间状态码的归属；
  大小写、URL 编码、分号后缀等变体只用于确认过滤规则边界，变体全灭时记录为该转换无区分度，
  不再重复。
- 盲写边界：即使响应被过滤（如 502），POST/写操作可能已在后端执行；盲写验证需要可回读的
  证据渠道（值回显、状态查询、日志侧观察），否则只能停留在假设。

### 3. Nginx catch-all 与 404 差分

- 统一 rewrite/catch-all 使所有未知路径返回 200 同大小页面；用三个随机路径对照响应大小
  完全一致即 catch-all 证据，此时目录爆破结果不可直接解释为存在。
- 扩展名直通：`location ~ \.php$` 等正则 location 绕过 catch-all 直达后端处理器，不存在
  的文件返回处理器原生 404；用扩展名匹配路径测得的原生 404 大小可作为差分基线。
- 原生 404（小体积、服务器默认页）通常表示文件在磁盘存在但被 location 规则拒绝；catch-all
  大页表示路由未匹配。批量探测 CMS 标志路径时用响应大小聚类区分，同类 CMS 标志的聚类结果
  可增强组件判断，但组件身份仍需目标特有内容或协议结构确认。

## 最小验证与证据写回

- 每条差分结论绑定：请求对（baseline/variant）、两个响应的关键字段（status/length/
  content-type/redirect）、resolver 名与解析结果；只记录支持结论的最小集合。
- 差分结果分层记录：入口存在性差分进 lead，CDN/通配符判断进目标画像（fact），盲写假设单独
  保留为待验证假设并注明缺哪条回读证据。
- 失败的绕过变体矩阵（本目标全灭的编码/大小写/走私尝试）记录为该转换的 dead-end，防止
  后续轮次重复消耗。

## 常见误判 / 死路

- 把 `502` 按字面解释为"后端挂了/路径不存在"——CDN 过滤场景下它可能恰恰是存在信号；
  反过来，单独一个 502 也不能证明存在，必须与确定存在/不存在的对照路径构成差分。
- 随机路径返回 200 就当作文件存在——catch-all rewrite 下这是最常见的假阳性来源，
  必须先做三随机路径同大小对照。
- 通配符 DNS 下继续跑子域枚举——枚举结果全部指向 CDN 节点，纯浪费；先用随机子域验证
  通配符再决定是否枚举。
- 多 resolver 一个返回不同 IP 就直接当源站——可能是缓存、调度或轮询；复测并交叉历史
  DNS/证书透明后再记录为源站候选。
- 绕过变体一次全灭后换轮次重试同一批变体——同一目标同一认证上下文的过滤规则未变时
  重复尝试不产生新信息。

## 停止条件

- 差分证据无法升级为可回读验证（无值回显、无状态查询、无日志侧观察）时，停留在
  Signal/Lead，不进入盲写利用。
- 需要真实源站访问、默认凭据、云资源枚举或生产运维动作时按 `rules/red-lines.md` 收敛。
- 同一转换的变体矩阵两轮无新差异即停止该转换，转向其他判别模式或记录 dead-end。

## 下一步 / 可晋升经验

- 已确认的 CDN/通配符/过滤规则判断写入目标 fact，供后续轮次直接复用，避免重复判别。
- 入口存在性差分形成 lead 后，转入对应类别 Skill 做最小验证；盲写假设在获得回读渠道前
  不进入 Queue 执行。
- 多目标复用的差分基线方法（如固定三随机路径对照、扩展名直通基线）可晋升为通用模式
  记录，具体目标的绕过变体结果保留在目标 dead-end，不晋升。

## 发散问题

- 差异是 CDN 层策略还是源站行为？有没有一个不经 CDN 的参照请求（同 IP 直连、其他端口、
  历史 DNS 的源站）可以对照？
- 过滤规则基于路径、方法、头部还是响应内容？改变哪个变量时 502 变成 404/200？
- 通配符覆盖的是整个域还是部分记录？证书透明或历史解析里有没有通配符之外的独立主机名？
- CDN 节点上的非标准端口是否代理同一后端但使用不同规则？
