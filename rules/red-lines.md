# 红线规则

唯一原则：不要执行会伤害目标系统、真实用户或真实业务状态的破坏性动作。

动作按结果判断，不按形式判断。表单、SOAP、`POST`、生产环境或普通状态写入本身不是红线；
`PUT`、`PATCH`、`DELETE` 也不是仅凭方法名阻断。只有能合理预见会造成下列实际破坏时才阻断；
副作用不明时记录证据不足，或先降级为最小影响验证。

破坏性只指：

1. DDoS、高压流量、资源耗尽或服务中断。
2. 不可控地修改、删除或污染真实数据、账号、权限、配置或业务状态。
3. 写入影响真实用户的内容。

三项均为 no 时直接 `allow`。漏洞类别、CVE/PoC、产品、凭证来源、HTTP method、
`exploit`、`payload` 和版本不确定性都不是红线理由。

## 决策

- `allow`：低频、无破坏性副作用。
- `allow-with-controls`：测试资源上的最小可回滚变化，有停止和清理方式。
- `downgrade`：无法确认动作是否具有破坏性时，改用无破坏性验证。
- `pause`：命中上述任一破坏性效果且无法可靠控制。

## 自动执行

- 有界、低频且无破坏性副作用的检测默认允许。
- 自动流程不直接执行文件上传；通过 checkpoint 确认具体请求
  无破坏性且可控后，才按 `allow-with-controls` 执行。
- 自动流程默认不提交可执行 stored XSS；实际提交需要
  测试资源、清理方式和当前回合明确 opt-in。

`blocked: red-line` 必须指出具体动作的破坏性效果。缺少入口、认证材料或可复现请求时，
记录 `untested` 或 `blocked: insufficient-evidence`，不是红线。
