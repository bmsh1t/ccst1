## 两次包装失败与恢复复盘

根因属于执行包装的隐含假设/覆盖缺口，不是产品 hot_method 缺陷；没有为它修改产品代码。

| 尝试 | 证据与实际状态 | 处理 |
|---|---|---|
| 初次 bootstrap | guard 禁止列 C 根，Python namespace package 无法导入 tools；v1 manifest不变、history不存在 | 只允许列根目录以支持 import，不开放根文件读取；使用与验收相同的解释器 |
| retry-1 | `--unshare-all` 的 user namespace root 无法写真实 uid1000/mode0775 knowledge 父目录；7份正文已发布，manifest仍v1，有 pending、无 decision/receipt | 不改目录 owner/mode，不删 pending；修正包装后显式 recover complete |
| recover complete | 保留调用者 user namespace，仍隔离 mount/pid/net/ipc/uts/cgroup；cap-drop ALL，仅加 CAP_DAC_OVERRIDE | C 本地事务向前完成，applied、cleanup confirmed；之后才做 A6 和入口发布 |

`bootstrap-failure-inspection.json`、`bootstrap-pending-inspection.json` 与所有失败 stdout/stderr、
started/call 记录均保留；`cutover.py`/guard 的最初、retry1、retry2版本分别留存，成功调用绑定
实际版本 SHA。包装的 Python I/O guard 限源码/knowledge/显式任务输入，禁止目标/个人 runtime
读取及全部 socket/subprocess；网络 namespace 另行隔离。放宽 DAC 不是开放目标访问授权。

预防：在同形态混合 uid 目录演练包装的 import 与目录发布权限；绑定真实根/父目录；外层
调用前落 started/argv，超时留输出并报告“提交状态未知”，随后查 pending/receipt，不假定未写。
第一项 import 修正不能解决另一独立的 DAC 边界，不能反复盲重试或 chmod/chown 来绕过。
恢复只处理当前事务；不回放 Store 快照，不撤销已产生的目标数据或证据。
