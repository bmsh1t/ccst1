# F10：披露查询失败与缓存保全

## 目标

查询失败不覆盖上次成功材料，不把失败标记为新鲜空查询；让读取披露材料的 agent 明确
区分本次查询是否完整与材料实际年龄，而不是把网络不可用解释成没有已披露报告。

## 要求

- R1：区分全部已执行查询成功且零结果、部分查询失败、全部查询不可用，以及过期但可读
  材料。查询异常或坏响应不得降成成功空列表；一次查询失败不阻止独立健康查询继续。
- R2：全部查询失败或 client 不可用时，不新建成功空缓存，不覆盖已有缓存字节或刷新其
  cached_at_ts。上次有效成功材料仍可读，展示时注明过期及实际成功时间。
- R3：部分失败必须显示有界诊断并保留本次健康查询结果，不能仅凭列表非空显示完整成功。
  采用保全方案：任何实际查询失败均不替换成功缓存；本次有报告则展示 partial 新材料，
  本次没有报告则展示有效旧快照（若有），保留其真实时间并说明本次 partial。
  不混合新旧快照，不持久化逐关键词来源；program 失败后 keyword 成功仍须显示 partial。
- R4：完整成功刷新按现有路径保存材料，合法零结果仍可成为新的成功快照。健康 TTL 命中
  不执行查询、不更新成功时间；显式 `--no-mcp` 保持不读取／修改缓存、不加载 client 或
  target inventory 的既有行为。非有限 TTL 拒绝，避免 NaN 绕过过期比较；有限 TTL≤0
  保持强制刷新的使用方式。
- R5：坏缓存不能成为有效旧材料；查询同时失败时，不以新空快照覆盖其原字节。发布失败
  必须显式失败并保留对应旧完整文件，不把写失败报告为成功。provider 的 search 响应
  不能将缺失／错误 envelope 抹成成功空列表；合法无 report 节点及可选字段保持兼容，
  已提供的错误类型即使为假值也不能被当作缺失。
- R6：保留缓存 owner、路径、成功 payload、查询上限、关键词 fallback 与 CLI 调用方式；
  不增加持续诊断状态、评分、缓存框架、依赖或自动迁移，不改变报告推理与技术判断。

## 已确认取舍

在单一保全方案的确认问题后，用户要求继续。R3 采用“保留完整成功缓存、展示 partial 新
结果”的策略；代价是下次可能重复已成功的查询，而不是丢失未成功重查的旧报告。
本次无新报告时使用一份有效旧快照，避免把“partial 零结果”当成没有历史材料。
只有实际执行的查询全部成功才更新缓存；没有计划的 similar 查询不算失败。
